# CYUKTI End-to-End Correlation Trace

For each hop in `WAZUH -> AttackEvent -> Campaign -> Operation -> Investigation -> Evidence -> ResponsePlan -> Playbook -> Shuffle execution -> MISP event`, the *actual* correlation mechanism, not an assumed one. No hop below relies on undocumented timestamp inference — every real relationship is either a stored Neo4j edge, an explicit foreign-key-style field, or a direct in-memory object reference, and each is named.

| Hop | Mechanism | Where |
|---|---|---|
| Wazuh alert → AttackEvent | `realtime_socgraph.process_alert()` calls `mitre_resolver.resolve_mitre(alert)`, then `neo4j_client.create_attack_event()` / `create_unattributed_attack_event()`, which `MERGE`s a real `(:AttackEvent)` node and a real `(:AttackEvent)-[:MATCHES]->(:Technique)` edge when a technique was resolved. | `realtime_socgraph.py`, `neo4j_client.py` |
| AttackEvent → Campaign | `campaign_manager.resolve_campaign()` creates/reuses a `(:Campaign)` node and links it via `(:Campaign)-[:HAS_EVENT]->(:AttackEvent)` and `(:Attacker)-[:LAUNCHED]->(:Campaign)` — a real stored edge, not inferred from proximity in time. Continuation vs. new-campaign is a genuine decision (`CampaignDecisionEngine`, 7 weighted features), not "same attacker within N seconds." | `campaign_manager.py`, `campaign_decision_engine.py` |
| Campaign → Operation | `operation_manager`/`campaign_correlation_engine` create/attach `(:Operation)-[:HAS_CAMPAIGN]->(:Campaign)` — real edge, queried directly in `dashboard_api.incident_overview()` (`MATCH (o:Operation)-[:HAS_CAMPAIGN]->(c:Campaign {campaign_id: $id})`). | `operation_manager.py`, `campaign_correlation_engine.py`, `dashboard_api.py` |
| Campaign → Investigation | `investigation.loop.run_investigation()` takes a `CampaignContext` object directly (in-memory reference, not a DB join) — the investigation's evidence store is keyed to that exact context for the duration of the run. Not persisted as its own Neo4j entity; see "Known gap" below. | `investigation/loop.py` |
| Investigation → Evidence | Each `InvestigationAction`'s executor constructs `Evidence` objects (`evidence/schema.py`) with `relationships`/`derived_from` fields naming the specific campaign/technique/evidence IDs they came from — a real, explicit reference chain inside the `EvidenceStore`, not merely "collected around the same time." | `investigation/actions.py`, `evidence/schema.py` |
| Evidence/Investigation → ResponsePlan | `soar.response_plan.ResponsePlanGenerator.generate(campaign, playbook, qualification, selection)` takes the *same* `CampaignContext`, `Playbook`, `ThreatQualificationResult`, and `SelectionResult` objects as direct Python references — verified by `test_final_trace.py`'s explicit `plan.playbook is playbook` (identity, not just equality) assertion. | `soar/response_plan.py` |
| ResponsePlan → Playbook | `ResponsePlan.playbook` **is** the `Playbook` object (not a copy or a re-fetched one); `Playbook.source_campaign_id` names the exact campaign it was generated for. | `soar/schema.py`, `soar/generator.py` |
| Playbook → Shuffle execution | `soar.execution_service.PlaybookExecutionService.request_execution(playbook, campaign_id)` creates a `PlaybookExecution` row with `playbook_id`/`playbook_version` foreign keys into `soar.memory`'s SQLite store — a real relational reference. | `soar/execution_service.py`, `soar/memory.py` |
| Shuffle execution → MISP event | **Not directly linked today.** `PlaybookExecution` and MISP publication (`misp_sync.py`/`misp_cache.py`) are two independent subsystems — a playbook's `create_incident`/`notify_soc` actions do not currently write back a MISP event ID onto the `PlaybookExecution` record, and `misp_cache.json`'s campaign→event_id mapping has no field referencing which `PlaybookExecution` (if any) triggered it. **This is a real, documented gap**, not a hidden assumption: the two are correlated today only indirectly, by both being keyed to the same `campaign_id`. |

## Known gap: Investigation has no persisted Neo4j identity

Unlike Campaign/Operation/AttackEvent, an `investigation/loop.py` run is not itself written to Neo4j as a queryable entity with its own ID — it's a request/response object (`POST /api/investigate/<campaign_id>` → `InvestigationRecord`, returned and discarded). This means "Campaign → Investigation" is a real, direct call (the campaign context is *passed into* the investigation, not looked up by some correlation key), but there is no way to later ask Neo4j "show me every investigation that ran against campaign X" — only "run one now." `IncidentOverview['investigation_available']` reflects this: it tells the frontend investigation *can* be run, not that one *has* been, because that history isn't persisted anywhere to report.

## Verification

`backend/tests/test_final_trace.py` constructs this exact object chain (ALERT → MITRE → CAMPAIGN → THREAT QUALIFICATION → CAMPAIGN SELECTION → RESPONSE PLAN → PLAYBOOK → MISP DECISION) with real production classes and asserts identity/reference equality at each hop, not just similar-looking output. It does not touch Neo4j/GNN/Shuffle/MISP — it proves the Python objects are wired together; the Neo4j-edge hops above were verified separately, live, in `FULL_SYSTEM_INTEGRATION_AUDIT.md` and `INCIDENT_VIEW.md`'s real Nmap-scan investigation.
