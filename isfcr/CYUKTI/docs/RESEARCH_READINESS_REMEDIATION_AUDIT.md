## 1. CAMPAIGN CORRELATION AND LIFECYCLE

### 1.1 Reported Issue

**Source**: `evaluation/results/campaign_correlation_metrics.json`

**Measured Performance**:
- 3 real independent sessions
- 46 campaigns generated by CYUKTI
- Session fragmentation: 4, 17, and 25 campaigns
- Pairwise precision: 0.0
- Pairwise recall: 0.0
- Pairwise F1: 0.0
- Adjusted Rand Index: 0.0
- Cluster purity: 1.0 (misleading under severe fragmentation)

**Example**: Session `SCN-SESSION-BOUNDARY-002::192.168.56.106->pes1ug23cs411-VirtualBox` was fragmented into 25 separate campaigns.

### 1.2 Root Cause Analysis

**Investigation Findings**:

#### Campaign Identity Model
- **Location**: `backend/campaign_manager.py::_key()`
- **Current Implementation**: Campaign identity is based solely on `(attacker_ip, victim_ip)` tuple
- **Issue**: No session boundary concept exists in the correlation model
- **Code Evidence**:
  ```python
  def _key(self, attacker_ip, victim_ip):
      return (attacker_ip, victim_ip)
  ```

#### Campaign Lifecycle
- **Active Campaign Resolution**: `resolve_campaign_context()` retrieves ONLY ONE active campaign per (attacker, victim) pair
- **Closure Logic**: Campaigns close when correlation score < `ACTIVE_CONTINUE_THRESHOLD` (0.30)
- **Reopening Logic**: Fast reopen requires exact match: `first_technique == current_technique and temporal >= 0.8`

#### Temporal Handling
- **Timeout**: `CAMPAIGN_TIMEOUT` causes campaigns to expire
- **Late Events**: Properly handled with `_later()` function
- **Event Time**: Event-time semantics are correctly implemented

#### Correlation Features
- **Location**: `backend/campaign_feature_engine.py`
- **Weights**: transition_similarity (0.35), temporal_similarity (0.25), attacker_similarity (0.15), lateral_movement_similarity (0.15), runtime/graph/duplicate (0.10)
- **Transition Similarity**: Scores 0.1 for unseen transitions (neutral), not 0.0
- **Issue**: Even with these improvements, fragmentation persists

### 1.3 Specific Defect: Campaign Continuation Failure

**Hypothesis**: Campaigns are closing prematurely despite related events occurring within the timeout window.

**Evidence Needed**:
1. ✅ Measured fragmentation: Confirmed (46 campaigns from 3 sessions)
2. ⚠️ Correlation scores at closure: NOT YET EXAMINED
3. ⚠️ Temporal gaps between fragments: NOT YET EXAMINED
4. ⚠️ Feature values during fragmentation: NOT YET EXAMINED
5. ⚠️ Reopen candidate evaluation: NOT YET EXAMINED

**Classification**: GENUINE IMPLEMENTATION DEFECT

**Proposed Resolution**:
1. Add comprehensive logging to campaign correlation decisions
2. Create test dataset with known session boundaries
3. Instrument correlation scoring to understand why related events score < 0.30
4. Determine if threshold, feature weights, or feature calculations are causing premature closure
5. Implement session boundary hints or temporal continuity improvements
6. Test: same attacker/victim, same session vs. different sessions
7. Test: delayed events, out-of-order events, campaign closure edge cases

**Regression Risks**:
- Over-merging: Different sessions may be incorrectly merged
- Performance: Additional correlation logic may impact latency
- Determinism: Replay behavior must remain consistent

**Acceptance Criteria**:
- Related events within the same real session should correlate (target: F1 > 0.75)
- Different sessions with the same attacker/victim must remain separate
- Pairwise precision ≥ 0.90 (avoid false merges)
- Pairwise recall ≥ 0.80 (reduce fragmentation)
- Campaign closure must be explainable and reproducible
- All existing tests continue to pass
- Deterministic replay behavior preserved

## 2. EVIDENCE-AWARE INVESTIGATION

### 2.1 Reported Issue

**Source**: `review/phase21_real_investigation_results.json`

**Key Finding**: "Action order and every selection_value were identical (to 3 decimals) across all 3 real campaigns, despite different techniques, risk scores, and model outputs."

**Evidence**:
- All 3 real campaigns executed identical action sequence: `["mitre_knowledge", "xgboost_prediction", "graph_structure", "campaign_history", "detection_check", "cti_lookup", "attribution_match", "mitre_semantic_search"]`
- All 3 campaigns had identical selection values: `[1.74, 1.73, 1.62, 1.49, 1.485, 1.135, 0.875, 0.3]`
- All 3 stopped at max_steps=8, never triggered confidence-based stopping

**Classified As**: "disclosed negative/limiting result, not a bug"

### 2.2 Root Cause Analysis

**Investigation Findings**:

#### Non-Adaptive Action Selection
- **Location**: `backend/investigation/next_best_evidence.py::score_action()`
- **Issue**: `uncertainty_reduction` is nonzero ONLY for `XGBOOST_PREDICTION` action
- **Issue**: All other action scores depend only on static `ActionMeta` constants or which action TYPES were already taken, not on evidence CONTENT
- **Result**: Since all 3 campaigns exhausted the same 8-action universe, order was deterministic and identical

**Code Evidence** (from report): "uncertainty_reduction is nonzero only for XGBOOST_PREDICTION; all other terms are static ActionMeta constants or depend only on which action TYPES were already taken, not on evidence CONTENT."

#### Single-Pass Model Execution
- **Issue**: "The current investigation loop runs the model verdict at most once"
- **Issue**: "New evidence does not update the model's features"
- **Result**: Investigation cannot adapt based on newly collected evidence

#### Confidence Estimation
- **Hand-set Constants**: Confidence uses hardcoded thresholds
- **Not Calibrated**: Confidence is not a calibrated probability
- **Uncertainty**: Calculated as `1 - confidence` (not genuine information-theoretic uncertainty)

#### Stopping Policy
- **Fixed Thresholds**: confidence > 0.75, entropy < 0.4, max_steps = 8
- **Observation**: All 3 real campaigns had final confidence 0.07-0.18, never reached 0.75 threshold
- **Result**: Only max_steps stopping criterion was exercised

### 2.3 Classification

**Adaptivity Limitation**: DOCUMENTED LIMITATION, NOT A BUG
- The report correctly classifies this as a "disclosed negative/limiting result"
- The mechanism works as designed, but the design has known limitations
- This is ACCEPTABLE for a capstone project IF properly documented

**Single-Pass Model Execution**: INCOMPLETE IMPLEMENTATION
- The investigation should theoretically update and re-evaluate as new evidence arrives
- Current implementation does not support this feedback loop
- This IS a gap between stated research direction and implementation

**Classification**: INCOMPLETE FUNCTIONALITY + DOCUMENTATION DEFICIENCY

**Proposed Resolution**:

1. **Adaptivity Architecture** (Optional Enhancement):
   - Create modular NBE selection framework supporting multiple strategies
   - Implement baselines: Random, Fixed-Order, Reliability-Greedy, Current CYUKTI
   - If implementing information-gain-based selection, use defensible probabilistic formulation
   - Document equations and assumptions explicitly
   - Compare strategies in ablation study

2. **Investigation Feedback Loop** (REQUIRED):
   - Implement multi-pass investigation loop:
     a. Gather available evidence
     b. Evaluate evidence quality  
     c. Calculate current investigation state
     d. Select next-best evidence
     e. Acquire/process evidence
     f. Update evidence graph
     g. **Recompute relevant investigation features**
     h. Update confidence and uncertainty
     i. Re-evaluate investigation decision
     j. Select next action OR stop
   - Ensure loop cannot run indefinitely (max actions, time budget, duplicate prevention)
   - Preserve investigation trace for reproducibility
   - Maintain API compatibility

3. **Confidence Calibration** (REQUIRED):
   - Review confidence calculation formula
   - If not mathematically justified, rename as "confidence score" not "probability"
   - Implement calibration evaluation infrastructure
   - If labeled data unavailable, explicitly state "uncalibrated"

4. **Stopping Policy** (REQUIRED):
   - Make thresholds configurable
   - Add explicit termination reasons
   - Test: sufficient evidence, insufficient evidence, conflicting evidence, budget exhaustion

**Regression Risks**:
- Investigation behavior changes may affect downstream components
- Performance: Multi-pass execution may increase latency
- Compatibility: Investigation API changes must be backward-compatible

**Acceptance Criteria**:
- Investigation loop supports multiple passes with feature updates
- Newly collected evidence can trigger model re-evaluation
- Stopping reasons are explicit and logged
- Investigation traces are reproducible
- Existing investigation tests pass
- Documentation clearly separates calibrated vs. uncalibrated claims
