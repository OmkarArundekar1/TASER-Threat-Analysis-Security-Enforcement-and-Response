# CYUKTI Accuracy / Evaluation Framework

## The honest starting point

CYUKTI has multiple distinct tasks, each requiring its own metric — and, critically, **independently-verified ground truth is not equally available for all of them in this environment.** This document says plainly, per task, whether real numbers can be reported here or whether only the measurement infrastructure exists, waiting for real labels.

## A. Tasks with real, already-computed evaluation (prior phases)

- **GNN historical campaign retrieval** — `ml/gnn/retrieval_evaluation.py`, documented in `GNN_RETRIEVAL_EVALUATION.md`. Leave-One-Attacker-Group-Out (LOGO) cross-validation, grouped by real attacker IP (a raw identity fact, never by a derived similarity score) — the correct way to avoid the "don't use CYUKTI's own similarity score as ground truth" trap this phase's rules explicitly warn against.
- **Severity/XGBoost prediction ablation with GNN embeddings** — `ml/gnn/xgboost_ablation.py`, documented in `GNN_XGBOOST_ABLATION.md`. Also LOGO-based. Result: no measurable benefit from adding GNN embeddings (a real, frozen null result — **not reopened or modified this phase**, per rule 17).

Neither of these is duplicated or re-run by this phase's new `evaluation_metrics.py` — they already have their own purpose-built, leakage-safe evaluation code.

## B. Tasks with NO independently-verified ground truth in this environment

- **MITRE mapping accuracy.** This lab's "attacks" come from a synthetic traffic generator (bracket-tagged log lines like `LOGIN_ATTACK`, `BOT_ATTACK`, `INVENTORY_ABUSE` — see `MITRE_MAPPING.md`). Using CYUKTI's own resolved MITRE IDs, or the generator's own attack labels, as "ground truth" to score CYUKTI's own mapping would be circular — this phase's own critical rules explicitly forbid exactly that ("do not calculate metrics against labels generated by the same mapper being evaluated"). Wazuh's *native* rule mappings (e.g. rule 5716 → T1110) are vendor-provided and could arguably serve as one small, independently-sourced reference set, but that is a single-digit sample of rules, not a dataset.
- **Threat classification (NOT_THREAT/SUSPICIOUS/QUALIFIED_THREAT).** Same problem: no analyst has manually reviewed and labeled a set of real incidents in this environment as actually malicious vs. benign, independent of CYUKTI's own scoring.
- **Campaign/operation correlation.** No independently-labeled "these alerts truly belong to the same real-world campaign" dataset exists — the campaigns are themselves CYUKTI's own correlation output.
- **Playbook recommendation effectiveness beyond raw success/failure.** The SOAR layer (prior phase) tracks real `success`/`failed` execution outcomes once playbooks actually run — but zero real Shuffle executions have occurred yet in this environment (`SHUFFLE_INFRASTRUCTURE_BLOCKED`, `SOAR_PLAYBOOK_INTEGRATION.md`), so there is no outcome data to compute a success rate FROM yet, real or fabricated.

**No numbers are reported for A/B/C/D/H/I from the original task list in this environment.** Reporting them would mean either fabricating labels or measuring CYUKTI against itself — both explicitly prohibited by this phase's own rules ("never fabricate accuracy metrics," "use independent ground truth").

## What this phase built: the measurement infrastructure (`evaluation_metrics.py`)

Ground-truth-agnostic metric functions, ready to use the moment real labels exist for any of the tasks in section B:

- **Classification**: `precision_recall_f1`, `classification_report` (per-label + macro/micro/weighted F1, balanced accuracy, exact-match accuracy), `false_positive_negative_rates`, `multilabel_exact_match_ratio` (for multi-technique alerts).
- **Clustering/correlation**: `pairwise_precision_recall_f1`, `cluster_purity`, `campaign_fragmentation` (over-merging vs. over-fragmentation, reported separately).
- **Retrieval**: `recall_at_k`, `mean_reciprocal_rank`.

17 tests (`test_evaluation_metrics.py`) verify each function against hand-computed values (perfect prediction, known error patterns, edge cases like empty/no-match inputs) — the functions themselves are correctness-tested even though no CYUKTI-specific dataset is run through them yet.

## What would be needed to fill section B in

For each task: a human (or an independent, non-CYUKTI-derived source) reviewing a sample of real alerts/campaigns and recording what they actually were, kept completely separate from anything CYUKTI itself computed. Given this lab's synthetic traffic generator, the most defensible near-term option is manual review of a sample of real Wazuh alerts once the corrected rule mappings (`MITRE_MAPPING.md`) have been live for a period, cross-checked by a second reviewer.

## Accuracy dashboard

Not built as a separate section this phase, consistent with section A/B above: a dashboard showing metrics with no real data behind them would itself be a form of fabrication. Once section B has real labeled samples, `evaluation_metrics.py`'s output is already JSON-serializable dict data, trivially renderable in a dedicated page following the same pattern as `SystemHealthPage.tsx`/`ThreatIntelligencePage.tsx` built in prior phases of this session.
