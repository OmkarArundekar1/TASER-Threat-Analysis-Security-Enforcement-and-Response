# CYUKTI Decision Auditability

For each major decision, whether the system retains: input, evidence, decision, score, threshold, decision source, timestamp, output.

| Decision | Retained? | Where | Fields actually persisted |
|---|---|---|---|
| MITRE resolution | **Yes, fully, live-verified this phase.** | `AttackEvent` node (Neo4j) | `mitre_status`, `mitre_provenance`, `mitre_confidence`, `mitre_reason`, `mitre_resolver_version`, `mitre_technique_ids` — real, confirmed on the actual Nmap-scan event: `provenance=NATIVE_WAZUH`, `confidence=CONFIRMED`, `reason="Wazuh rule.mitre.id"`, `resolver_version="1.0.0"`. (A first check without `ORDER BY e.first_seen DESC` accidentally matched an older, pre-this-field event and returned nulls — corrected; not a real gap.) |
| Campaign correlation | **Partial.** | `Campaign` node properties + `CampaignDecisionEngine` | The *outcome* (which campaign an event joined) is persisted via the `HAS_EVENT`/`LAUNCHED` edges. The 7-feature *decision breakdown itself* (`CampaignDecisionEngine`'s per-feature scores/threshold) is computed in-memory per alert and not written back to Neo4j as its own record — so "why did this event join campaign X rather than start a new one" is reconstructable only by re-running the decision function with the same historical state, not by querying a stored breakdown. |
| Severity | **Yes.** | `Campaign.risk_score`/`Campaign.total_tps`, `SeverityResult.breakdown` | Score is persisted; the per-feature `breakdown` dict (platform/mitigation/threat-actor/malware/tool weights) is returned to the caller but not itself written to Neo4j — same partial pattern as campaign correlation. |
| Threat qualification | **Yes, fully, live-verified.** | `Campaign.cti_score`, `Campaign.cti_publish`, `Campaign.cti_breakdown`, `Campaign.cti_updated_at` | Real, confirmed live: e.g. `CAMP_1627943B` → `score=53.38, publish=False, updated_at=2026-08-09T18:54:43Z`. The six-check `ThreatQualificationResult` (added this session) is *not* separately persisted — it's recomputed on demand from the stored score via `_build_threat_qualification()`, deterministically (see `DETERMINISM.md`), so nothing is lost, just not stored as its own row. |
| Campaign selection | **No.** | n/a | `BestCampaignSelector.select()` is a pure, on-demand computation (`GET /api/campaign-selection/<id>` / `.../overview`) — never persisted. A repeat query recomputes it fresh (deterministic given the same underlying data, per `DETERMINISM.md`) rather than replaying a stored decision. |
| NBE (Next-Best-Evidence) | **No.** | n/a | Computed per investigation step, returned in `InvestigationStepResult.why_selected`/`candidate_actions`/`action_scores`, but the investigation itself isn't persisted (see `CORRELATION_TRACE.md`'s "Known gap") — so NBE reasoning survives only as long as the HTTP response that carried it. |
| Investigation stopping | **No**, same reason as NBE. | n/a | `stopping_reason` is a real field in the response but not written anywhere durable. |
| ResponsePlan | **No.** | n/a | Generated fresh on each `GET /api/incidents/<id>/response-plan` call. Deterministic given the same playbook/qualification/selection inputs (`DETERMINISM.md`), so re-generating it reproduces the same plan — but there's no historical log of "what plan was shown to the analyst at time T," only "what plan would be shown right now." |
| Playbook selection (generate vs. reuse an existing one) | **Yes.** | `soar.memory.PlaybookMemoryStore` (SQLite) | `playbooks` table (`source_campaign_id`, `adapted_from_playbook_id` lineage), `playbook_executions` table, and `soar_audit_events` table (`PLAYBOOK_GENERATED`, `PLAYBOOK_ADAPTED`, `PLAYBOOK_APPROVED`, etc., each with `timestamp`, `campaign_id`, `playbook_id`, `execution_id`, `detail`). This is the most completely audited decision in the system. |
| MISP publication decision | **Partial.** | `Campaign.cti_publish` (the gating score/bool) | The gate's *input* (`cti_score`) and *outcome* (`publish` bool) are persisted on the Campaign node. Whether a publish attempt was actually *made* and what happened (`misp_sync.py`'s `success`/`action`/`reason` return value) is not written back to Neo4j — only to the transient response and `misp_cache.json` (event_id mapping only, no decision trail). |

## Summary

Fully audited (input→decision→output, durably, with timestamp): **MITRE resolution**, **threat qualification** (score/threshold), **playbook selection/execution**. Computed-on-demand, reproducibly, but not durably logged as a historical decision record: **campaign selection, NBE, investigation stopping, ResponsePlan**. Partially audited (outcome stored, full breakdown not): **campaign correlation, severity, MISP publication**.

## Honest framing

None of the "computed on demand" rows are silently non-deterministic guesses — `DETERMINISM.md` proves each recomputes identically given the same inputs. The real limitation is narrower: CYUKTI cannot currently answer "what exact ResponsePlan/NBE reasoning did the analyst see at 14:32 last Tuesday if the underlying campaign data has since changed" — only "what would it compute now." Closing that would mean persisting a versioned snapshot of these computations per investigation session, which is a real, scoped follow-up (a `soar_audit_events`-style table for investigation/selection/response-plan generation, mirroring what already exists for the playbook lifecycle) rather than a redesign.
